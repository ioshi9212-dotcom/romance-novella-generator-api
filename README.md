# Генератор новелл: первый этап

Минимальный backend для **создания новеллы и подготовки игрового контекста**. Генерации сцен и самостоятельного симулятора NPC здесь нет. Создание истории, подготовка хода, сохранение, откат и подготовка/фиксация аудита уже реализованы; литературные правила остаются в Skin Builder. Текущие шаблоны истории находятся в `state/`.

## Развёртывание в Amvera

В корне есть `amvera.yaml`: Python 3.12, зависимости из `requirements.txt`, команда запуска `uvicorn app.main:app --host 0.0.0.0 --port 8000`, входящий порт 8000 и постоянное хранилище `/data`.

В интерфейсе Amvera в разделе **«Переменные»** укажите:

- `API_KEY`: собственное длинное случайное значение, **секрет**, не добавляйте ключ в GitHub или переписку;
- `DATA_DIR`: `/data`, обычная переменная.

Проверьте, что Amvera развёртывает **именно этот репозиторий/актуальный код** и что постоянное хранилище действительно подключено. После изменения переменных перезапустите приложение. Проверка доступности API: `GET /health` без ключа. Главная страница `/` не предусмотрена; ответ 404 на ней сам по себе не означает сбой. `GET /docs` показывает документацию API, но игровые запросы требуют заголовок `X-API-Key`.

Истории, RAW и персональные данные сохраняются на диске по пути `/data/sessions/<session_id>/`, а не в публичном GitHub. Не используйте папку с исходным кодом как постоянное хранилище.

## Rules, Skin Builder и интерфейс ChatGPT

- `runtime/rules.md` — **действующий технический протокол** для текущего API: создание, загрузка, чтение контекста, точечные обновления, commit, повторные запросы и восстановление после сбоя. Без правил сцены, решений POV/NPC и художественной подачи. Содержит реально доступные процедуры, включая аудит, откат и продолжение сессии.
- `runtime/scene_builder.md` — **пустой Skin Builder**. Литературные правила позднее заполнит автор.
- `gpt/custom_gpt_instructions.md` — короткая **основная инструкция для игрового GPT** (менее 8000 символов): роль, приоритет канона/Rules/Skin Builder, команды взаимодействия и оформление выбора/сообщений.

**Важно:** текстовая инструкция задаёт поведение GPT и способы оформления ответа, но не создаёт собственный веб-фронтенд на Amvera. Чтобы элементы появились в игровом GPT, его конфигурация должна использовать `gpt/custom_gpt_instructions.md`. Сам API не рисует кнопки. Наличие файла в GitHub без подключения к инструкциям GPT ничего в интерфейсе не меняет.

Базовый API не зависит от этих файлов, поэтому пустой Skin Builder не ломает существующие `prepare-turn` и `commit-turn`.

## Подключение ChatGPT GPT Actions

1. После развёртывания свежего коммита в Amvera открой редактор своего GPT. В поле **Instructions** вставь полностью текст `gpt/custom_gpt_instructions.md` (он проверяется на максимум 8000 символов).
2. В разделе **Actions → Create new action** вставь `openapi.json` или импортируй ссылку `https://raw.githubusercontent.com/ioshi9212-dotcom/romance-novella-generator-api/main/openapi.json`. Это отдельная схема на **19 действий**, включая создание новеллы, подготовку/сохранение, аудит, откат, сжатие и продолжение.
3. Настрой **Authentication → API Key → Custom Header** с заголовком **`X-API-Key`**. Укажи тот же секрет, что в переменной `API_KEY` в Amvera. **Не включай значение ключа в инструкцию, YAML/JSON, GitHub или переписку.**
4. В Preview сначала проверь `checkHealth`, затем `getRuntimeInstructions`. Второй запрос требует настроенной аутентификации и возвращает `rules`, `skin_builder`, их `sha256` и признак `changed`. При неизменённом хеше возвращаются пустые тексты, чтобы не гонять одинаковые правила.
5. Запусти **новую тестовую новеллу**, убедись, что создание сохраняет RAW, а ID возвращается сервером. Не проверяй запись на ценном существующем игровом ходе до подтверждения настройки.

`runtime/rules.md` и `runtime/scene_builder.md` читаются **из развёрнутой версии сервера** через авторизованное `GET /runtime`. Изменения файлов в GitHub становятся доступными после новой сборки Amvera. Текст инструкции в самом GPT (поле Instructions) обновляется вручную при изменении `gpt/custom_gpt_instructions.md`.

API возвращает данные и сохраняет историю; он **не создаёт настоящие интерфейсные кнопки**. Варианты выбора будут интерактивными только если клиент ChatGPT поддерживает соответствующий интерфейс, иначе отображаются как обычный текст.

## Запуск

```bash
pip install -r requirements.txt
export API_KEY='your-private-key'
export DATA_DIR='./data'    # в Amvera установите /data
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Все запросы, кроме `GET /health`, требуют заголовок `X-API-Key`. Содержимое сессий и RAW хранится исключительно в `DATA_DIR/sessions/<uuid>/`, **не в GitHub**. Для запуска на Amvera нужны подключённое постоянное хранилище и переменные `API_KEY`, `DATA_DIR`.

## Этапы создания

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/runtime` | Прочитать актуальные Rules/Skin Builder с кешированием по sha256 |
| `POST` | `/sessions` | Создать сессию; `request_id` делает создание повторяемым, `initial_text` необязателен |
| `POST` | `/sessions/{id}/raw` | Сохранить дословно порцию материала. `event_id` обязателен, повторы безопасны |
| `GET` | `/sessions/{id}/raw` | Перечитать весь RAW для сверки |
| `POST` | `/sessions/{id}/advance` | Перейти к следующему этапу |
| `PUT` | `/sessions/{id}/data` | Записать один заполненный JSON документ |
| `GET` | `/sessions/{id}/data?path=...` | Заново прочитать JSON для проверки |
| `POST` | `/sessions/{id}/verify` | Проверка целостности данных и завершение подготовки |
| `GET` | `/sessions/{id}` | Текущее состояние подготовки |
| `POST` | `/sessions/{id}/prepare-turn` | Прочитать согласованный контекст следующего игрового хода, ничего не меняя |
| `POST` | `/sessions/{id}/commit-turn` | Сохранить сцену и точечные изменения одним восстановимым ходом |
| `POST` | `/sessions/{id}/prepare-audit` | Прочитать точные последние 15 сцен и память для проверки |
| `POST` | `/sessions/{id}/commit-audit` | Записать проверенные исправления, не создавая игровой ход |
| `POST` | `/sessions/{id}/rollback-last-turn` | Откатить последний ход, восстановить файлы и архив |
| `GET` | `/sessions/{id}/resume` | Продолжить сохранённую сессию в новом чате |
| `GET` | `/sessions/{id}/turns` | Получить до 15 старых сцен |
| `POST` | `/sessions/{id}/prepare-compaction` | Подготовить проверяемую сводку после 60-го хода |
| `POST` | `/sessions/{id}/commit-compaction` | Записать проверенную долговременную сводку |

Порядок: `сбор` → первое `подтверждаю` → `вопросы` → `вопросов_больше_нет` → `готово_к_записи` → второе `подтверждаю` → `запись_и_сверка` → запись и многократная проверка JSON → `verify` → `готово_к_игре`. Повторную команду подтверждения сервер **не переинтерпретирует** как следующую.

### Примеры JSON

`POST /sessions`:
```json
{"request_id":"novel-draft-123","initial_text":"Мой первый материал о мире..."}
```

`POST /sessions/{id}/raw`:
```json
{"event_id":"answer-001","question":"Какой год начала?","text":"1206 год"}
```

`PUT /sessions/{id}/data`:
```json
{"path":"карточки/char_002.json","document":{"id":"char_002","имя":"Эйден","фамилия":"Вернер"}}
```

`POST /sessions/{id}/verify`:
```json
{"audited_against_raw":true,"unresolved_issues":[]}
```

## Подготовка игрового хода (`prepare-turn`)

Доступна после успешного `verify` и не меняет номера хода, фазу или какие-либо файлы.

Пример первого запроса:

```json
{"user_input":"(Продолжить разговор и открыть сообщение)"}
```

Ответ включает:

- текущий `state.json`, анкету, компактную **полную** хронологию, весь короткий реестр и отношения;
- **полные** карточки и личную память только физически присутствующих и активно участвующих удалённо персонажей, включая POV;
- короткий индекс **всех** активных крючков и тайн, а полные записи только для уже загруженных персонажей или выбранных индексов;
- полную запись текущей постоянной локации, краткий индекс остальных;
- последние две подтверждённые сцены из `ходы.jsonl`, если архив существует;
- введённое игроком сообщение дословно, `turn_id` будущего хода и хеш собранного контекста.

Если режиссёр видит в коротком реестре повод для самостоятельного действия NPC вне сцены, **до написания этого действия** нужно вызвать тот же маршрут повторно с полным списком выбранных персонажей:

```json
{"user_input":"(Продолжить разговор и открыть сообщение)",
 "additional_character_ids":["char_aiden"],
 "selected_hook_indices":[1],
 "additional_location_ids":["archive"]}
```

Второй вызов возвращает один полный пакет со всеми данными первого плюс выбранными карточками, **полной** личной памятью, соответствующими тайнами и локациями. Не требуется цепочка мелких запросов по одному файлу; нет ограничения по числу записей в памяти и тихого отбрасывания старых фактов. Если NPC не нужен сейчас, его полное досье не читается. Нахождение имени в вводе игрока само по себе не разрешает автоматически переносить знания героя в сцену.

Полная хронология сейчас читается целиком, потому что важные старые причины нельзя молча отбрасывать по возрасту записи; её дальнейшее сокращение производится аудитом и сжатием, а не произвольным техническим лимитом. При росте числа ходов размер контекста необходимо измерять.

Общие Rules и Skin Builder **на этом этапе не подключены**. В будущем Rules содержит только техническую механику, Skin Builder автор создаст отдельно. Сервер не принимает решения за персонажей.

## Сохранение хода (`commit-turn`)

После подготовки `prepare-turn` и написания сцены GPT передаёт весь **новый текст сцены** и только изменившиеся поля данных. Передаются `turn_id`, `user_input`, `context_sha256` из последнего подготовленного пакета. Если контекст расширяли дополнительными персонажами/крючками/локациями, их параметры **обязательно повторяют** в `commit-turn`.

```json
{
  "turn_id": "<session_id>:1",
  "user_input": "(посмотреть на Эйдена)",
  "context_sha256": "<64 шестнадцатеричных символа из prepare-turn>",
  "scene": "Эйден поднял взгляд от записей...",
  "additional_character_ids": ["aiden"],
  "updates": {
    "память/aiden.json": [
      {"op": "append", "path": "/личные_события/13.10.2026", "value": {"с_кем": ["pov"], "событие": "Обратил внимание на татуировку Елены."}}
    ],
    "персонажи.json": [
      {"op": "merge_by_id", "path": "/персонажи", "value": {"id": "aiden", "последняя_встреча": "Кофейня"}}
    ]
  }
}
```

> Важное уточнение: пути к элементам массивов не используются. Для изменения одной записи реестра можно передать `set /персонажи` с актуальным коротким списком целиком. Для остальных документов используйте пути к объектам, например `/период_суток`, `/знания/13.10.2026`, `/личные_события/13.10.2026`.

**Операции над полями:** `set` записывает значение по пути, `append` добавляет элемент в список (создаёт пустой список при первом добавлении), `merge_by_id` обновляет отдельную запись списка по неизменному ID без пересылки всего реестра, `remove` удаляет существующее поле. Пути соответствуют JSON Pointer. Все операции применяются к **уже существующим документам**, старые знания и события не нужно присылать снова. Для **новой** карточки или памяти допускается `set` с пустым путём `""` и полным новым объектом, но только совместно с регистрацией персонажа в реестре.

Сервер перед записью проверяет актуальность контекста, допустимость файлов, то, что уже существующие персонажи предварительно загружены, и техническую целостность всей будущей структуры. Если проверка не прошла, **не меняется ничего**. Если запись оборвалась после начала сохранения, одиночный служебный журнал `.pending_turn.json` позволяет завершить её при следующем обращении к сессии. Архив `ходы.jsonl` содержит ввод, полный текст сцены и данные до/после изменений для проверки и будущего отката.

Повтор того же запроса для сохранённого `turn_id` возвращает `already_saved`, **не создавая дублирующую сцену**. Подмена текста уже сохранённого хода, неверная версия контекста и переписывание чужой непогруженной памяти отклоняются. Неизменные файлы не переписываются. `prepare-turn` возвращает только тексты последних сцен, а не технические снимки из архива.

Сейчас **нет** автоматического написания сцен и самостоятельного смыслового аудита силами сервера. API отката, 15-ходового аудита и проверенного 60-ходового недеструктивного сжатия работают. Сводки пишет и проверяет модель; сервер только обеспечивает целостность. Rules технические, Skin Builder пока пуст.

## Аудит каждые 15 ходов и откат

После сохранения ходов №15, №30, №45 и далее `GET /sessions/{id}` возвращает `аудит_требуется: true`. До завершения проверки следующие `prepare-turn` и `commit-turn` ответят `409 AUDIT_REQUIRED`.

**Проверка:** `POST /sessions/{id}/prepare-audit` с `{"character_ids":[]}` возвращает точные последние 15 сцен, текущие основные файлы, память непосредственно затронутых и присутствующих персонажей, а также `audit_sha256`. Дополнительную память можно догрузить повторной подготовкой по ID. Сам сервер не выдумывает забытые события: GPT сравнивает архив с файлами, затем вызывает `POST /sessions/{id}/commit-audit` с `through_turn`, `audit_sha256`, тем же списком выбранных ID, `reviewed_against_archive:true`, `findings`, `updates` и `evidence_turns`. Каждому изменённому файлу нужен хотя бы один исходный номер хода из проверенного диапазона. Пустые `updates` допустимы, если пропусков нет. Результат сохраняется в `аудиты.jsonl`.

**Откат:** `POST /sessions/{id}/rollback-last-turn` c `{"expected_turn_id":"<последний сохранённый turn_id>"}` восстанавливает документы `до`, удаляет последний архивный ход и возвращает номер хода назад. Если после хода был аудит с правками, он отменяется вместе с ним. RAW и прежние ходы сохраняются. Сеть/процесс может оборваться в середине операции: при следующем обращении сервер завершит её по служебному журналу `.pending_maintenance.json`.

На ходах №60, №120 и далее после аудита требуется проверенная моделью долговременная сводка: `prepare-compaction` → осмысленное составление сводок → `commit-compaction`. До неё следующий ход возвращает `409 COMPACTION_REQUIRED`. Исходные журналы памяти, хронология и полный архив сцен **не сокращаются и не удаляются**. Они всегда доступны для точной сверки.

## Продолжение сессии и длинная история (API 0.5.0)

- `GET /sessions/{id}/resume` даёт компактную точку входа **в ту же сессию**, включая ID, фазу, следующий номер хода, текущий State, короткий реестр, обзор сюжетных крючков, две последние сцены и статус аудита/сжатия. Не создавай новый ID и не копируй файлы между чатами.
- `GET /sessions/{id}/turns?from_turn=10&to_turn=15` возвращает точные сцены из архива. За раз можно запросить максимум 15 последовательных ходов. Архив остаётся источником для проверки деталей.
- Каждые 60 ходов после завершённого 15-ходового аудита вызывается `POST /sessions/{id}/prepare-compaction`. Ответ содержит предыдущую долговременную сводку, несжатую личную память, историю, проверенные выводы четырёх аудитов и краткий проверяемый индекс 60 сцен. Последние 15 сцен включены полностью, предыдущие можно получить через `turns`. После реальной проверки модель отправляет `POST /sessions/{id}/commit-compaction` с `through_turn`, `review_sha256`, `reviewed_against_archive:true`, `world_summary` и `character_summaries` по всем зарегистрированным ID.
- Результат хранится в сессии как `сводка_контекста.json` и содержит проверяемые отпечатки уже охваченных записей. В новых `prepare-turn` длинная старая память заменяется **сводкой плюс новыми записями**, а не удаляется из файлов. Режиссёрская хронология обрабатывается аналогично.
- Если для старого события требуется оригинал, подготовь ход с `full_memory_character_ids:["pov"]` (ID должен быть уже загружен через участие или `additional_character_ids`) и/или `full_chronology:true`. **Те же параметры** надо передать в `commit-turn`, иначе проверка контекста не совпадёт.
- Если кто-то исправил уже охваченный старый факт, сервер обнаружит изменение по хешу и автоматически вернёт **полный источник** вместо устаревшей сводки. Откат хода, на котором сделано сжатие, отменяет контрольную точку. Всё хранится в постоянном `DATA_DIR` на Amvera.

## Технические инварианты

- `raw.txt` хранит материалы в порядке поступления с маркерами источника. Оригинальный текст **внутри маркеров дословный**. Ответы на вопросы сохраняются с формулировками вопросов. `event_id` защищает от повторного добавления при сетевом сбое.
- Во время заполнения пишутся семь основных JSON: `анкета.json`, `персонажи.json`, `state.json`, `хронология.json`, `скрытый_лор_и_крючки.json`, `отношения.json`, `локации.json`, а также `карточки/<id>.json` и `память/<id>.json` для каждого персонажа, включая POV.
- ID персонажей постоянные. Чужая карточка, хронология и скрытый лор не являются личными знаниями NPC или POV. Реестр содержит короткие ориентиры; целые разговоры хранятся в личной памяти.
- Числовые параметры отношений только у NPC → POV, по шкале `0–100`, из известного словаря осей; NPC → NPC словесно. Отношений от имени POV нет.
- `verify` проверяет **структуру, ID и ссылки**, но не умеет автоматически установить смысловую полноту относительно RAW. Полную сверку должен самостоятельно выполнить GPT, перечитывая RAW и сохранённые JSON; поле `audited_against_raw` лишь подтверждает, что он эту проверку провёл. Нельзя считать `verify` независимым семантическим аудитом.
- Подготовка, сохранение, откат, архивный просмотр, аудит 15 ходов и проверенное сжатие 60 ходов реализованы. Автоматического художественного анализа сервер не выполняет.
- Сервер не обрабатывает бинарные вложения напрямую: текст, извлечённый из файла в ChatGPT, передаётся как `text` с необязательным `file_name`. Для точного сохранения оригинальных бинарных файлов потребуется отдельная загрузка.
- Код API описывает **только технику**. Никаких инструкций о стиле сцены, решениях POV или литературных приёмах здесь нет.
