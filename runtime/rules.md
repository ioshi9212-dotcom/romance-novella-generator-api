# Rules. Технический протокол

**Назначение:** порядок обращения к API, источники данных, загрузка контекста, проверка изменений и сохранение. Это не Skin Builder. Здесь нет режиссуры, правил диалога, решений POV или NPC, структуры и формата ответа, художественного стиля, сценарных обязательств.

## 1. Источники и границы

- **Backend хранит актуальные данные сессии.** Используй подтверждённые результаты API, а не догадки из предыдущих сообщений чата. Шаблоны в репозитории не являются заполненными данными конкретной сессии.
- `анкета.json` — канон и начальные условия новеллы; `хронология.json` — объективные значимые произошедшие события; `скрытый_лор_и_крючки.json` — режиссёрские тайны и незавершённые сюжетные линии.
- `персонажи.json` — короткий список по постоянным ID, с последней встречей и событием с POV, местонахождением и занятием. Эти короткие ориентиры не заменяют карточку или память. Если местонахождение/занятие не изменилось, не обновляй поле.
- `карточки/<id>.json` — постоянные сведения конкретного персонажа; `память/<id>.json` — его личные знания и пережитые события, включая незавершённые личные вопросы; `отношения.json` — текущие направленные отношения.
- `state.json` — точные участники, позиции, одежда, предметы и текущая ситуация сцены; `локации.json` — постоянные важные места. Для текущей сцены точный State имеет приоритет над кратким ориентиром реестра; расхождение исправляется по реально сохранённым событиям.
- **Режиссёрская информация не является памятью персонажа.** Чужие карточки, знания, скрытый лор, хронология, реестр и отношения сами по себе ничего не сообщают POV или NPC. Запись в личную память допустима только с доступным этому персонажу источником; чужое утверждение фиксируется как утверждение, а не автоматически как истина. Собственная карточка тоже может содержать неизвестное владельцу прошлое.
- `raw.txt` хранит первоначальные материалы дословно; `ходы.jsonl` хранит подтверждённые игровые ходы. Не подменяй файлы сессии локальными копиями документов из GitHub.

## 2. Создание новеллы

1. `POST /sessions` создаёт одну сессию. Сохрани полученный `session_id`. Повторная попытка создания с тем же `request_id` и тем же `initial_text` безопасна.
2. `POST /sessions/{id}/raw` добавляет каждый новый материал с постоянным `event_id`. Передавай текст дословно; для ответа на вопрос используй `question`, для извлечённого текста файла при необходимости `file_name`. Повторяй тот же `event_id` только с тем же содержимым.
3. `POST /sessions/{id}/advance` меняет этапы в строгом порядке: `сбор` + «подтверждаю» → `вопросы`; `вопросы` + «вопросов_больше_нет» → `готово_к_записи`; `готово_к_записи` + «подтверждаю» → `запись_и_сверка`. Это служебные команды, не игровые реплики.
4. На этапе `запись_и_сверка` заполняй документы через `PUT /sessions/{id}/data` и перечитывай `GET /sessions/{id}/data?path=...`. Сначала проверь, что информация не потеряна относительно полного `GET /sessions/{id}/raw`.
5. `POST /sessions/{id}/verify` вызывай **только после реальной смысловой сверки** с RAW и устранения разногласий. `audited_against_raw=true` не заменяет сверку: сервер проверяет JSON, ID и связи, но не смысл.
6. После успешного `verify` фаза `готово_к_игре`; первое `prepare-turn` готовит ход № 1. Команду запуска первой сцены не передавай как реплику/действие POV.

Не делай новую сессию после второго подтверждения и не записывай личные материалы новеллы в репозиторий.

## 3. Подготовка одного хода

1. Для каждого нового игрового ввода вызови `POST /sessions/{id}/prepare-turn` с **точным** `user_input`. До следующего хода используй один `session_id`.
2. Прочитай весь ответ. В нём: `turn_id`, `номер_хода`, `контекст_sha256`, исходный ввод, режиссёрский пакет, подробные карточки и память загруженных участников, последние две сцены. `prepare-turn` ничего не записывает и не увеличивает номер хода.
3. Сервер автоматически загружает полные карточки и память POV, физических и активных удалённых участников из `state.json`. Реестр и отношения читаются целиком; хронология читается целиком в текущей реализации. Краткий обзор **всех** крючков и тайн поступает вместе с подробностями записей, связанных с уже выбранными персонажами.
4. Если для текущего хода потребуется **ещё один** значимый персонаж вне сцены, до использования его личных данных повтори **тот же** `prepare-turn` с тем же `user_input` и `additional_character_ids`. При необходимости укажи `selected_hook_indices`, `selected_secret_indices`, `additional_location_ids`. Передавай **совокупный список** выбранных ID и индексов, а не только новые добавления. Повторный запрос возвращает заново единый расширенный пакет.
5. Не загружай все карточки подряд и не вызывай повторную подготовку ради простого упоминания имени. Индекс крючка или тайны в обзоре не заменяет полную запись, если нужны её подробности. Не добавляй отсутствующие сведения из предположений.
6. Используй `контекст_sha256` **последнего полного пакета**. Не смешивай карточки, индексные номера или хеши из разных подготовок. Если между подготовкой и сохранением изменились исходные данные, нужна новая подготовка.

Текущая версия API не использует `getTurnPacketChunk`, `prepareCharacterBundleRead` и прочие старые цепочки Roman AI. Не вызывай их.

## 4. Запись одного хода

`POST /sessions/{id}/commit-turn` получает:
- `turn_id`, `user_input` **дословно как при prepare**, `context_sha256` из последней подготовки;
- `scene`: полный готовый текст уже составленной сцены;
- `updates`: объект `{"имя_файла.json": [{"op": "...", "path": "...", "value": ...}]}` только для реально изменившихся данных;
- те же `additional_character_ids`, `selected_hook_indices`, `selected_secret_indices`, `additional_location_ids`, с которыми получен сохраняемый пакет.

В `updates` поддержаны:
- `set`: записать значение поля; `append`: добавить значение в массив; `remove`: удалить поле; `merge_by_id`: изменить поля **ровно одной существующей записи** массива по её `id`.
- `path` — путь JSON Pointer: `/знания/13.10.2026`, `/физически`, `/персонажи`. Пустой путь и `set` всего документа разрешены **только для нового файла**, например `карточки/new_id.json`.
- Для памяти по датам используй `append` в соответствующий массив, не заменяй весь накопленный дневник. Для короткого обновления одного уже существующего персонажа в реестре используй `merge_by_id` на `/персонажи`, а не переписывай весь список.
- Если изменений данных не было, отправляй `updates: {}`: полный текст сцены всё равно сохраняется и номер хода увеличивается.

**Куда записывать изменения:** объективное произошедшее → `хронология.json`; новые личные знания и события → `память/<id>.json` только соответствующего персонажа; актуальное отношение → `отношения.json`; физическое состояние и участники сцены → `state.json`; короткие текущие ориентиры NPC → `персонажи.json`; постоянная новая информация о персонаже → его карточка; значимые открытые сюжетные линии → `скрытый_лор_и_крючки.json`. Новому постоянному NPC нужны запись в реестре, карточка и личная память по одному ID.

**Техническая проверка отношений:** у NPC нет предопределённых названий параметров. Для каждого NPC→POV разрешены не более 10 свободно названных параметров, значения от 0 до 100, без отрицательных. NPC→NPC хранятся как короткие направленные текстовые связи. При `commit-turn` каждое число у уже существующего NPC может измениться на 0–3 за ход. Новый параметр по умолчанию начинается не выше 3, исчезнувший параметр сравнивается как 0; отсутствие обновления корректно. Для действительно критического события, уже произошедшего в сохранённой сцене, больший скачок у конкретного показателя допускается через `relationship_exceptions: [{"owner_id":"ID","parameter":"название","reason":"конкретная причина критического события"}]`. Сервер проверяет наличие осмысленной причины, но тяжесть события оценивает GPT по сцене. Не прикладывай исключения к обычным изменениям. Если `доверие` достигло 0, отдельное `недоверие` можно записать **только при наличии основания в событии**; никакой автоматической замены или отрицательных чисел нет. Новые NPC с заданными в их предыстории отношениями могут получить исходные значения при создании. Аудит нескольких старых ходов проверяй по исходным сценам, не притворяясь, что его суммарные исправления относятся к одному ходу.

Не сохраняй предполагаемое будущее как произошедшее. Не обновляй файл без реального изменения. Не записывай одно событие полностью в несколько мест: каждому файлу нужна только его собственная часть данных.

## 5. Проверка и сбои

Перед `commit-turn` проверь один раз:
- ID и присутствие POV; различие физического и удалённого участия; фактически изменившиеся позиции, вещи и активные каналы;
- соответствие обновлений итоговой сохранённой сцене; отсутствие утечек режиссёрских/чужих знаний в личную память; отсутствие повторов и непрошеного изменения неизменных полей;
- для внешнего значимого NPC — его карточка и память включены в последний пакет; имена файлов и ID совпадают; `turn_id`, хеш, `user_input` и выборки соответствуют последней подготовке.

**Один ход → один успешный commit.** После подтверждения `status=saved` можно считать результат сохранённым. На повтор того же **точного payload** сервер возвращает `status=already_saved` и не удваивает ход.

Если ошибка или таймаут, сначала прочитай `GET /sessions/{id}`: открой состояние сессии и номер последнего сохранённого хода. При неясном исходе допускается повторить **строго идентичный** commit; не создавай другую сцену с прежним `turn_id`. При `409` из-за устаревшего контекста повторно вызови `prepare-turn` и сверяй изменения с уже сохранённой историей, а не обходи конфликт. При `422` исправь невалидный запрос до повторения. Отсутствие ответа сети **не означает**, что данные не записались.

Сервер хранит промежуточную транзакцию и при следующем обращении к сессии пытается её завершить. Архив `ходы.jsonl` содержит полный ввод, сцену, ID хода и снимки изменившихся документов до/после. Старые игровые ходы не пересоздавай по памяти чата.

## 6. Откат последнего игрового хода

- Вызови `POST /sessions/{id}/rollback-last-turn` с `{"expected_turn_id": "<id последнего сохранённого хода>"}`. Операция **удаляет только последний** ход, а не произвольный старый. Несовпадающий ID возвращает `409`, не затрагивая данные.
- Сервер по архиву восстанавливает документы `до` этого хода, убирает его запись из `ходы.jsonl`, уменьшает номер хода и удаляет файлы NPC, созданные только отменённым ходом. Исходный RAW и предыдущие сцены не меняются.
- Если после этого хода был завершён аудит с исправлениями, его запись и изменения тоже отменяются, чтобы не оставались выводы из отменённой сцены. Аудит затем понадобится выполнить заново при достижении очередной границы.
- При ошибке/таймауте не запускай второй откат наугад. Проверь `GET /sessions/{id}` и, если нужно, повтори запрос с **тем же** `expected_turn_id`; ответ `409` может означать, что первый откат уже выполнен. Не откатывай очередной ход без явного намерения игрока.

## 7. Технический аудит памяти и данных

- Каждые 15 **сохранённых** ходов сервер ставит `аудит_требуется=true`. До закрытия аудита подготовка и сохранение следующего хода возвращают `409 AUDIT_REQUIRED`. Это контрольная точка, не автоматическое создание новых сюжетных фактов.
- Вызови `POST /sessions/{id}/prepare-audit` с `{"character_ids":[]}`. Получи **точные последние 15 архивных ходов**, текущие файлы и память персонажей, затронутых изменениями или присутствующих сейчас. Если по сценам нужен иной NPC, повтори `prepare-audit` с его ID: его личная память будет загружена для сверки. Проверяй реальное наличие знаний, сообщений, встреч, изменений отношений и непротиворечивость данных.
- Сверяй с текстом архива: присутствие само по себе не доказывает, что персонаж слышал частный разговор. Слова персонажа нельзя заменять объективным фактом. Не придумывай задним числом события и источники знаний. Изменения памяти разрешены только для персонажей, включённых в пакет аудита.
- В `POST /sessions/{id}/commit-audit` передай `through_turn`, `audit_sha256`, тот же `character_ids`, `reviewed_against_archive=true`, `findings`, `updates` и `evidence_turns`. Для каждого изменённого файла `evidence_turns` содержит номера архивных ходов, на которых основана правка. Пример: `{"память/aiden.json":[7,8]}`. Сервер проверяет диапазон и техническую корректность; правдивость связи между сценой и исправлением должна быть действительно проверена во время аудита.
- Пустые `updates:{}` допустимы: если ошибок нет, зафиксируй успешную проверку без лишних изменений. `commit-audit` не создаёт новый игровой ход; отдельный `аудиты.jsonl` фиксирует проверку и корректировки. Повтор идентичного запроса безопасен.
- При `409` из-за изменившегося `audit_sha256` повтори `prepare-audit` и сверку. Не делай исправления из чужих карточек или секретов, недоступных персонажу.
- На каждом 60-м ходе после обычного аудита потребуется отдельная **проверенная моделью** долговременная сводка, иначе следующий ход будет заблокирован `COMPACTION_REQUIRED`. Это не автоматическое сочинение сводки сервером.

## 8. Продолжение и длинный контекст

- Чтобы продолжить историю в новом чате, получи `session_id` прежней сессии и вызови `GET /sessions/{id}/resume`. Это **чтение**, не создание сессии и не игровой ход. По ответу определи текущий этап, номер хода и необходимость контрольной проверки. Затем используй стандартный `prepare-turn`.
- Для проверки конкретных старых сцен доступен `GET /sessions/{id}/turns?from_turn=N&to_turn=M`, максимум 15 последовательных ходов.
- Каждые 60 ходов **после завершения аудита** вызывай `POST /sessions/{id}/prepare-compaction`. Читай предыдущую сводку, свежую память и историю, краткий индекс 60 сцен, последние 15 полных сцен и результаты четырёх проведённых аудитов. Если нужно восстановить точную формулировку более ранних сцен, дочитывай соответствующие номера через `turns`.
- После проверки подготовь `world_summary` и `character_summaries` для **каждого** зарегистрированного ID. Не приписывай персонажам знания из режиссёрской истории. Вызови `POST /sessions/{id}/commit-compaction` с `through_turn`, `review_sha256`, `reviewed_against_archive:true` и сводками. `audited=true` не подменяет смысловой проверки.
- `prepare-turn` после сжатия возвращает **сводку старых данных и новые записи**. Полная память всегда остаётся в сессии. Для точной догрузки старого дневника используй `full_memory_character_ids`; для всей хронологии `full_chronology:true`. При `commit-turn` повтори идентичные параметры подготовки, иначе хеш не совпадёт.
- Если отпечаток старых записей не совпадает с контрольной точкой, сервер не скрывает данные: возвращает полный файл и признак `сжатие_недействительно`. Откат 60-го/120-го хода отменяет соответствующую сводку.
- Сводки и архив не содержатся в GitHub. Данные живут в постоянном хранилище сессии.

## 9. Остальные ограничения



- Архив читается по диапазону до 15 ходов. Сводка старой истории появляется только **после смысловой проверки моделью** и успешного `commit-compaction`; сервер самостоятельно не пишет художественные пересказы и не удаляет оригиналы.
- Не объявляй аудит, исправление памяти или сжатие выполненными без подтверждения соответствующей операции.
- Актуальные `runtime/rules.md` и `runtime/scene_builder.md` доступны через авторизованный `GET /runtime` (действие `getRuntimeInstructions`) после развёртывания обновления на Amvera. Предыдущий `sha256` позволяет не получать повторно неизменённый текст. Эти документы не заменяют данные конкретной сессии.
- Оформление кнопок и сообщений описано отдельно в `gpt/custom_gpt_instructions.md`. Формат ответа и повествование будут определены автором в Skin Builder и не относятся к этим Rules.
